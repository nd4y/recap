# recap

Конвейер транскрибации и суммаризации аудиозаписей:
NAS -> GPU-транскрибация с диаризацией (GigaAM v3 + pyannote, Windows-служба) ->
summary (локальная или любая OpenAI-совместимая LLM) ->
заметка в Obsidian + сообщение в Telegram.

Полное описание архитектуры и решений: [TZ.md](TZ.md).
Установка с нуля: [DEPLOY.md](DEPLOY.md).

## Состав

| Каталог | Что | Где работает |
|---|---|---|
| `recap-asr/` | сервис транскрибации + диаризации, эталон голоса владельца (нативная Windows-служба, без Docker) | GPU-хост |
| `llm/` | `Modelfile` производной модели Ollama (контекст 16k) | GPU-хост |
| `workflow/` | workflow n8n: код нод + скрипт деплоя через REST API | стек `n8n` на NAS |
| `stack/` | compose стека n8n + экспортер метрик конвейера + скрипт доставки заметок в vault | NAS, docker + планировщик |
| `grafana/` | дашборды: конвейер recap и движок n8n (импортируемые JSON) | Grafana |

Параметры установки — в env-файлах, примеры: `stack/.env.example`,
`stack/deliver-outbox.env.example`, `workflow/.n8n.env.example`.

## Метрики

Три эндпойнта в формате Prometheus, без аутентификации (только LAN): `/metrics` n8n на порту UI,
`recap-exporter` (реестр и outbox конвейера, порт 9819) и `/metrics` сервиса `recap-asr`.
Переход файла в `failed` workflow сам сообщает в Telegram. Дашборды — `grafana/recap.json` (конвейер)
и `grafana/n8n.json` (движок), подробности — DEPLOY.md, раздел «Метрики».

## Потоки

- Источник: `<recordings>/<Подкаталог>/` на NAS, подкаталог = тип записи (звонок, встреча, голосовая заметка).
- Заметки: outbox -> штатный API NAS (планировщик) -> `Notes/Recordings/<год>/` в Obsidian vault -> клиент синхронизации разносит по устройствам. Прямые записи в ФС клиент синхронизации не видит, потому outbox.
- Telegram: summary + транскрипт вложением, только для записей свежее `RECAP_TG_MAX_AGE_DAYS` (дефолт 2 дня).

### Голосовые и видеокружочки из Telegram

Пришлите или перешлите боту голосовое сообщение либо видеокружочек в личный чат,
указанный в `TELEGRAM_CHAT_ID`. Recap скачает файл, распознает речь, пришлёт выжимку
ответом на исходное сообщение и полный транскрипт `.md` вложением. Заметка также
попадёт в Obsidian. `/start` и `/help` показывают инструкцию.

Приём выполняется перед сканированием записей каждые 5 минут, обработка зависит
от очереди. Бот принимает записи только из настроенного личного чата. Автор
пересылки может быть скрыт; чужая речь не считается речью владельца.
Возраст пересланной записи не отключает отправку результата в Telegram.
При отсутствии распознанной речи бот сообщит об этом. Текущий ASR пропускает
записи короче `RECAP_MIN_DURATION` (по умолчанию 5 секунд); бот также сообщит
о пропуске. Для распознавания коротких записей установите `RECAP_MIN_DURATION=0`
в окружении службы ASR.

Файлы сохраняются в `<recordings>/Telegram/` с JSON-метаданными рядом, offset
Telegram хранится в `<state>/telegram-offset.json`. Повторная доставка одного
update не создаёт второй файл. После трёх неудачных скачиваний бот сообщит об
ошибке и продолжит очередь. Повторная ручная пересылка создаёт новую запись.
Ошибки приёма не останавливают обработку записей на NAS.

Используется `getUpdates`; у этого бота не должно быть webhook или другого
потребителя входящих update. Облачный Telegram Bot API ограничивает скачивание
файла 20 МБ: большие записи следует положить в каталог записей на NAS.
Для включения обновите workflow через `workflow/deploy_workflows.py`; новых
переменных окружения и сервисов не требуется. Для отката восстановите прежний
workflow из резервной копии; сохранённые входящие файлы остаются на NAS.

Проверка Code-нод без сетевых запросов и личных записей: `node workflow/test_telegram.js`.

## Секреты

В репозитории секретов нет: токены Telegram и Hugging Face, `chat_id` и ключ внешней LLM живут в env стека и в env службы (в `recap-asr-service.xml` плейсхолдер).
